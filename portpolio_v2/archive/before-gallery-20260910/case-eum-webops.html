Case 06 이음 + WebOps Builder · 개인 프로젝트 · 2025.08 –

기획한 흐름을,직접 구현하고 검증했습니다.

팀과 설계했던 사용자·운영자 흐름을, 개인 프로젝트에서는 양쪽 화면 모두 직접 구현했습니다. 이음은 저장한 것을 필요한 시간과 장소에서 다시 떠올리게 하는 앱이고, 그 앱의 문의·신고를 처리하는 콘솔은 직접 만든 WebOps Builder입니다. 두 화면은 다른 제품이지만 한 사람의 같은 판단에서 나왔습니다.

기간
2025.08 – 진행 중
팀
혼자 — AI 코딩 도구와 함께
내 역할
기획 · 화면 · 구현 · 검증 — 사용자 앱과 운영 콘솔 양쪽
범위
이음 — 저장 · 분류 · 백업 · 리마인드 앱(Flutter, Android 우선) / WebOps Builder — 이음 문의·신고를 처리하는 개인 운영 콘솔
지금
이음 — MVP 구현 · 릴리스 빌드 검증 · 스토어 출시 전 / WebOps Builder — 비공개 개인 운영 도구

01

양쪽 화면이 다 필요했다

회사에서는 사용자 흐름과 운영자 흐름을 나눠 설계하고, 구현은 팀이 맡았습니다. 개인 프로젝트에서는 둘 다 제 몫입니다. 이음은 저장한 것을 필요한 시간과 장소에서 다시 떠올리게 하는 앱이고, 앱을 내놓으면 곧바로 문의와 신고가 들어옵니다. 사용자 화면만 만들고 끝낼 수는 없었습니다.

그래서 두 화면을 한 프로젝트로 봤습니다. 사용자가 쓰는 앱과, 그 앱을 운영하는 콘솔.

02

흐름을 다섯 단계로

저장은 쉽고, 다시 꺼내는 건 어렵습니다. 그래서 저장 → 분류 → 백업 → 리마인드 → 완료를 한 줄로 두고, 각 단계에서 사용자가 해야 할 입력을 줄였습니다. 외부 공유로 바로 저장하고, 시간은 템플릿으로, 장소는 지오펜스로 다시 알립니다.

홈 화면의 “함께 만드는 이음”은 사용자가 보낸 의견이 반영되는 과정을 보여주는 자리입니다. 의견을 받는 화면이 있으면, 처리하는 화면도 있어야 합니다. 그 화면이 다음 장입니다.

User 이음 — 저장에서 완료까지 한 줄

  1. 01저장메모 · 링크 · 이미지 · 쇼핑리스트 — 외부 공유로 바로 저장
  2. 02분류기본 카테고리 + 사용자 카테고리 · 수신함 필터
  3. 03백업로컬 우선 저장 · 재로그인 시 복원
  4. 04리마인드시간(템플릿 · 직접 선택) · 장소(지오펜스) · 외출 모드
  5. 05완료떠올린 것을 처리하면 끝

·홈의 “함께 만드는 이음” — 사용자가 보낸 의견이 반영되는 과정을 보여주는 자리입니다.

03

운영 화면을 직접 설계하다

회사에서 CMS를 기획하며 공통 기능과 고객별 기능을 나눴던 경험을 바탕으로, 개인 앱을 위한 운영 콘솔을 새로 설계하고 AI와 함께 구현했습니다. 회사의 소스를 옮긴 것이 아니라 경험을 옮긴 것입니다.

문의·신고 화면은 목록 · 원문 · 답변 · 상태 변경으로 구성했고, 작성자 식별정보는 콘솔에서 가립니다. 동작은 답변 보내기 · 상태 변경 · 확인 세 가지뿐이며, 각 동작이 무엇을 하는지 화면 위에 먼저 적어 두었습니다. 운영자가 저 혼자여도, 규칙은 화면에 있어야 한다고 봤습니다.

Operator 직접 만든 WebOps Builder — 이음 문의·신고 화면

1작성자 식별정보는 콘솔에서 가림2동작마다 무엇을 하는지 화면 위에 먼저 정의3답변 보내기 · 상태 변경 · 확인 — 세 동작뿐비공개 개인 운영 도구 · 문의 본문과 식별자는 이미지에서 가림 · 파란 밑줄은 포트폴리오 표시

Result 결과와 배운 점

  1. 이음
    MVP 기능 구현 · 릴리스 빌드 검증.

    스토어 출시를 준비하고 있습니다.

  2. WebOps Builder
    비공개 개인 운영 도구로 이음 문의·신고 관리에 사용.

    콘솔에는 다른 메뉴도 있지만, 이 사례는 실제로 쓰고 있는 문의·신고 화면만 다룹니다.

  3. 배운 것
    기획한 것을 직접 구현·검증하면, 개발팀과 나누는 말이 정확해진다.

    개발자를 대체하려는 것이 아니라, 기획 의도를 검증하고 더 정확하게 소통하기 위해 배우는 것입니다.
